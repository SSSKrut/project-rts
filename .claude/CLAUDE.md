## Build & Run

```bash
go run .                                                 # Build and run main (raylib dev libs required)
go build -o bin/rts .                                    # Compile main binary
go build -o bin/particle_sandbox ./cmd/particle_sandbox  # Compile sandbox
```

**Binary naming convention.** Always build into `/bin/<name>` — `/bin/` is the single .gitignore entry that catches every compiled artifact. Never `go build` without `-o bin/...`; the default would drop the binary at the repo root and slip past the per-target gitignore lines. Two ~9 MB blobs (`rts-go`, `particle_sandbox`) were purged from history in 2026-05 — don't add a third.

### Load-bearing design calls (short excerpt — full version in `GAMEDESIGN.md`)

- **Buildings live in surface coords (Layer 0).** No separate logical layers, no portal teleportation. Walls / doors / windows / stairs / floors are ordinary entities with `WorldPos` in the same frame as terrain. Cross-LOS through windows = ordinary raycast against the scene.
- **Windows = LOS-transparent walls; doors = traversal points.** Closed doors block both. Wall blocks both. This is how interior↔exterior combat works without layer transitions.
- **Bunker = building with a sunken footprint.** No SDF/voxel deformation. Heightmap-cut around the entrance, floors below ground level, stairs as the entry. SDF/voxel is frozen — see ROADMAP archived phases.
- **Static world objects are a single `Prop` abstraction.** Trees, bushes, rocks, fences, bridges, lamp posts — `WorldPos + PropType + Transform`. Gameplay attributes (cover, blocks-LOS/movement, hp) come from a `PropTypeRegistry` keyed by `TypeID`, not from the mesh. Lets us swap placeholder mesh → loaded model without touching gameplay.
- **Roads are a `RoadGraph` singleton resource.** Affects heightmap (a cut, never a fill), nav (road-bias for infantry — Phase 6/8; vehicles route over the graph via `RoadRouter` time-cost Dijkstra — Phase 19 M2), rendering. Bridges = sub-edges with `Kind = RoadBridge`, auto-tagged at startup by `PreprocessRoadGraph` where a road crosses a river polyline. **The visible road is a ribbon mesh, not props** (Phase 17.5-ROADS): `gen/ribbons` derives a smoothed, terrain-following deck from the graph once at boot; the gap down to the ground is closed by embankment geometry, and anything standing on the carriageway rides the deck via the `RoadSurface` resource — the bridge deck is just the tall case of that. Rivers = `Stamper.RiverCut` + a water-surface ribbon.
- **Smart Objects.** Props and buildings *emit* cover slots and shooting points; AI reads these instead of computing geometry.
- **Hierarchical AI.** Strategic (10–30 s) → Operational (1–5 s) → Tactical (per tick). Only the top tier may ever be a neural net; tactical stays classical (BT/Utility AI).
- **Squad = abstract invisible entity** (`CommandRoster`, `FormationData`, `RadioNetwork`), not "the units selected with a marquee".
- **Unit ≠ one component.** Split into Spatial / Senso-Cognitive / Execution / Equipment. Weapons / grenades / radios are *separate entities* with `OwnedBy{ownerEntityId}`. No arrays inside Unit components — kills DOD.

## Architecture

This is a 3D RTS/FPS prototype using **Ark ECS** (`github.com/mlange-42/ark/ecs`) for entity management and **raylib-go** for rendering/audio. The project migrated from a custom ECS to Ark — the old architecture docs about archetypes, WorldState, CommandBuffer, Scheduler etc. are obsolete.

### Core loop (root package)

`main()` is ~30 lines: `bootGame()` → `registerSystems()` → spawn → `initUI()` → `for !rl.WindowShouldClose() { g.RunFrame() }`.

Everything that used to be a local of the old 2955-line `main()` lives on **`Game`** (`game.go`), grouped by domain: `Res` (world resources) / `Maps` (`ecs.Map`) / `Filt` (`ecs.Filter`) / `Svc` (services + factories) / `Ctx` (render context structs) / `Sel` (selection + hover) / `UI` (panels, menus, editors) / `Dev` (debug block) / `Frame` (per-frame scratch crossing phase boundaries) / `Scene` (scripted `-scene` harnesses).

**`Game` must never be copied.** Resources are registered as `ecs.AddResource(world, &g.Res.X)` — the world holds pointers into the struct, so a copy silently leaves them aimed at the original. Always `*Game`, allocated once.

Where to make a change:

| I want to… | File | Seam |
|---|---|---|
| add a sim system | `boot_systems.go` | `(g *Game) registerSystems()` — construct + `InitUI` + `AddSystem`, order = per-tick pipeline |
| add a world resource / service | `boot.go` | `initResources()` / `initServices()` |
| spawn something at startup | `boot_scene.go` | `spawnWorldRoots()` / `spawnScene()` |
| add a Map / Filter / ctx struct | `boot_scene.go` | `initGameplayHandles()` / `initRenderHandles()` |
| add a hotkey or LMB behaviour | `frame_input.go` | `handleInput()` |
| touch RMB orders | `frame_orders.go` | `handleOrders()` |
| touch panel chrome / floaters | `frame_chrome.go` | `handleChrome()` |
| add a 3D draw pass | `frame_render3d.go` | `drawScene3D()` |
| add a 2D panel / HUD element | `frame_draw.go` | `drawUI()` |
| add a UI singleton / widget | `frame_ui.go` | `initUI()` + the widget methods |

**Frame phase order is a contract** (`frame.go`, `RunFrame`): `beginFrame` → `handleChrome` → `updateTestScenes` → `handleInput` → `handleOrders` → `updateHover` → **sim advance (exactly once)** → `drawScene3D` → `drawUI`. Input feeds the sim; the render half reads the post-tick world. `compactAlive` sits between the tick and the render half because units die inside `Advance` and Ark's `Map.Get` panics on a dead entity. Do not reorder phases without a reason written down.

`g.Frame.AnchorPos` points into ECS storage and is deliberately re-fetched after the tick — an archetype change during `Advance` can move the component.

**Teardown** is `g.Shutdown()` (chunk flush → worker pool → trace → font → window) plus `g.shutdownUI()` (underlay → scene RT → layout save → material), deferred in that order so LIFO reproduces the original sequence.

Runs after `order_resolver`, before `survival_instinct`; Active-only, one decision per squad every `squadBrainCadence` ticks (hash bucket, ~1.5 s). Output is `SquadPlan` on the Squad entity (POD, save_spec, hashed) — read by `FormationSystem` (slot targets) and `SurvivalInstinct` (who may take cover). Three modes, no more: **Bounding** (a march under fire splits by roster parity, `SquadPlan.Anchor` = one bound ahead along the macro path, the moving wave drives to it while the covering wave holds and shoots; wave flips on arrival or `boundPhaseMax`, exits after `boundCalmHold` of quiet), **Relocate** (half the roster standing in an `UnsafeArea` freezes the slot pushes while the men clear it under their own overrides, resumes after `relocateCleanFor` clean seconds), **ClearSeq** (StackUp beside the door → Enter with the point pair → Sweep storey k, and `plan.Floor` only advances when storey k holds no hostile — that gate IS the behaviour). Standing rules pin the brain the same way they pin the instinct: `HoldUntilOrdered` / `!AllowAutoReposition` force Mode=None (ClearSeq excepted — sequencing an explicit order is not autonomy). One phase transition per decision, so a phase can never be skipped inside a single call. `RTS_BRAIN_OFF=1` silences the tier for A/B scene runs.
  - **Interior slots** (Phase 19.8, `building_slots.go` + `building_slot_assign.go`): the planner decides WHICH positions matter, the matcher decides WHO takes them. `fillRoomSlots` clamps every room slot into its room's AABB with a 0.6 m inset (the raw Loose scatter reaches 2×spacing, outside any small room) and pushes it off transit circles — doorways and both landings of every stair flight — because a man parked on one corks the storey. Clamped positions go through `components.Normalize`: nav resolves a target via `Pos.Chunk`, so an absolute coordinate left in `Local` aims the walker at the wrong chunk. `assignSlots` is **slot-major over the planner's priority order** — each position picks its best available man by delivery cost (XZ + 15 m per storey). Globally-cheapest-pair greedy optimises total cost and schedules badly: near slots go first and an important far one waits for whoever is left. Ownership (`LocalBlackboard.HeldSlot`, index+1 so zero reads as "none") is **sticky, not a bonus** — the storey term flips the instant a climber reaches a landing, so any bonus loses and two men swap slots mid-stairs. When men are scarce the TAIL of the slot list is dropped, never the expensive pairs, or a far room ends up empty. A man under `TacticalOverride` is not a candidate: his slot goes to someone who can walk to it.
  - `ContactSystem` (Phase 18.5, absorbed the Phase 7 VisionSystem) — Active 250 ms ONLY (`RelevantEvery = LODDisabled`: the unit filter is not tier-scoped, so one pass covers every unit; a second tier call would double-run the detect pass and double-advance the FoW clock). Per-seer: sensor-channel detect (effective-range × Falloff curve × FacingProfile × concealment), audio bubble (constants in `audio_detect.go`), wall-LOS raycast inside a chunk window sized from the group's VISUAL reach (`detectGroup.span = ceil(maxRange / ChunkSize)`; windows/open doors transparent, closed doors/walls block) plus a terrain-LOS probe against the heightmaps (PHASE-VISION) — what still does NOT occlude is a FLOOR PLATE, so an upper-storey defender is seen and shot from the storey below (19.5 MC3 finding, Vision-track item). Vehicles participate both ways (Phase 19 M3): as targets (`DimVehicle`, concealment = spec DetectMul >1, audio = NoiseRadiusM moving / ×0.25 idling) and as seers via their own Sensors. Targets standing inside a live `SmokeField` get concealment ×0.35 (M4). Aircraft participate both ways too (Phase 20 M1, `snapshotAircraft`): as targets (`DimAir`, `targetY` = the actual altitude, signature by altitude band — `airConcealMul` 0.55 at NOE rising to 1.4 in transit, `airNoiseMul` the other way round, so low is quiet to the eye and deafening to the ear) and as seers. Two caps that never bit while everything saw 40-65 m had to go: the **chunk window was a silent ceiling on range itself** (fixed ±1 chunk ⇒ a 420 m radar was clipped to 76 m — hence `span`, sized from visual reach only, since audio needs no walls) and the **group cull threw away audio louder than any eyes** (`reach` now includes the loudest candidate on the field, which is what makes a helicopter heard at 229 m by a hull with 60 m optics). Walls stop occluding once the pair is separated vertically by `airWallClearM` (20 m, above the tallest generated building) — `losWall` is a 2D record with no top, so the alternative is walls that block the sky. `systems.PassiveSensorProfile` is the single answer to "how far does this set IMAGE": it skips ESM (kilometres that no raycast could ever justify) and honours `Sensors.OffMask`. Exported on purpose — the hold-V preview promises "the same predicates as ContactSystem" and can only keep that by asking the same function, or it draws a hull a 700 m visibility fan on a channel that sees no bodies. Writes `Awareness.LastSeen` FIFO + upserts `Contact` entities; combat-evidence / close-range promotion post-passes. `contact_emitter.go` adds the **passive pass** (Phase 20 M1, P4): a live `SensorESM` channel hears any hostile emitter at `min(emitter.EmitRangeM, esm.BaseRangeM)` and files a BEARING — no facing, no LOS, no detection meter, no range. It runs after the visual upsert so anything actually seen this tick already owns a real track, and it **never touches `Awareness`** (which feeds pickTarget a position that a bearing does not have — writing the emitter's true coordinates there would make ESM strictly better than eyes). **The FIFO holds hostiles only** (19.5 MC3): every consumer (pickTarget, UtilityEvaluator's nearest-enemy, the vehicle reflex's `engaging`) filters same-faction entries anyway, and recording squadmates overflowed the 8 slots for any full 8-man squad — the enemies were being evicted by friends, so a squad could not keep a target in memory.
  - `SurvivalInstinctSystem` (Phase 15, reworked through 19.5) — the per-unit half of reactive behaviour: ScatterProtocol on the squad, position scoring + `TacticalOverride` per man (see `survival_instinct_position.go`). Two MC3 gates sit in front of the scorer: a unit **inside any building footprint is left alone** (every candidate the scorer knows is terrain-derived, so "taking cover" indoors means walking off a storey or out of the room the order put the man in — interior positions are a P4 tail), and under a Bounding plan the **moving wave never acquires cover** (an override halfway to the bound is the old cover-freeze that stopped squads advancing) while the covering wave keeps its ordinary threshold — it holds its ground and shoots instead of racing to the nearest tree. `protection` scores a candidate two ways and both must land on the SAME scale: a cover normal contributes its dot with the incoming bearing (1.0 head-on), so `maskProtection` interpolates the 8-way mask between the **two bracketing compass sectors only** (19.8 fix — a cos²-weighted vote across the whole forward hemisphere capped a squarely-blocking wall at 0.5, because the flanking unmasked sectors always diluted it, and mask-derived cover silently lost every ranking).
  - `LODSystem` — assigns LOD marker components by distance to anchor with hysteresis. Excludes `TerrainChunk`, `Prop`, and `BuildingMember` — each of those archetypes has its own LOD owner.
  - `MovementSystem` — position += velocity * dt per LOD tier (separate Filter per tier).
  - `SpatialAudioSystem` — per-chunk voice limiting + distance-based volume/pan.
  - `StreamingSystem` — node graph traversal, updates `StreamingMap` resource.

  - `CameraSystem` — syncs ECS camera state to `systems.CurrentCamera` (global `rl.Camera3D`) and updates `CurrentOriginChunk`.
  - `AudioManager` — voice pool for multiple instances of same wave.
  - **Service objects (not Systems)**: `Stamper` (`systems/stamp.go`) — applies `HeightKernel` deltas to live chunks. Methods: `StampHeightmap` (sets `Modified`), `RiverCut` / `Trench` (cosine cut along polyline, no `Modified`), `RoadCarve` (per deck sample, lowers toward deck−subgrade with a cosine skirt; never raises, no `Modified`), `RectCut` (flat plate inside an `AABB2D` with cosine skirt outside, no `Modified`). Helpers `RiverCut` / `Trench` share a private `cutAlongPolyline`.

Called once from `main.go` before `InitUI`. Building layout generation lives in `gen/buildings/` (`GenerateHouse` / `GenerateOffice` / `GenerateCompound`) — see the `gen/` layer below.

Migrated from the old `systems/building_gen/`.

No ECS: terrain arrives as `Sampler func(wx, wz) float32`. Locked by `gen/ribbons/ribbons_test.go`.

### Key patterns

**LOD via marker components.** LOD state is represented by adding/removing `LODActive`/`LODRelevant`/`LODDormant` marker components. This changes the entity's archetype, enabling cache-friendly filtered iteration per tier via `ecs.FilterN`.

**Tick scheduling (WS-B, 2026-07).** The sim runs on a fixed 60 Hz timestep: `App.Advance()` (called once per render frame) runs `int(TimeScale)` ticks of `core.SimDt` (stops 1/2/4/8/16/32, Phase 19.7 M2), stopping early once the frame has spent `core.AdvanceBudget` (24 ms) inside the sim — the first tick is never skipped, so a TimeScale=1 run (every gate) can't be truncated and `App.Throttled()` only ever reports display state (`32x (cpu)` in the top bar); 0 = paused (one zero-delta pass keeps camera orbit alive; `OrbitSystem` applies mouse input once per frame via a FrameIndex guard). `App.Tick(delta)` remains as the raw entry for sandboxes. Each tick calls `system.Update` **once per enabled tier**, passing `ctx.Tier`. `LODPolicy` controls per-tier cadence: `0` = every tick, positive duration = throttle, `core.LODDisabled` (-1) = skip the tier. CAUTION: if a system's filters are not tier-scoped, enabling a second tier re-runs the full pass (the old ContactSystem 2× FoW-clock bug) — Active-only unless filters differ per tier. **Canonical clock:** `ctx.SimNow` (float64 seconds) + `ctx.TickIndex`; systems must NOT keep private elapsed accumulators. **Determinism:** two headless runs of any ai_* scene must produce identical state-hash logs — `./bin/rts -scene=ai_X -replay-hash=path` (FNV-1a over units/orders/contacts every 100 ticks, `systems/replay_hash.go`); full gate: `scripts/replay_gate.sh`. For a change that must be **behaviour-preserving** (refactors), `scripts/replay_baseline.sh` is stronger: it diffs every hash log against a saved reference build, so it proves bit-identity rather than mere self-consistency. Snapshot a reference first — `scripts/replay_gate.sh && mkdir -p .claude/baseline/replay && cp /tmp/rts-replay/*_1.txt .claude/baseline/replay/`. Both gates run headless ai_* scenes, which return before the render half: they cover boot / spawn / sim / save-load completely and only *compile-check* `drawScene3D` / `drawUI`. Render and UI changes still need a manual playtest. **Scene worlds are pristine**: ai_*/door scenes get a fresh per-process temp `SaveDir` (`bootGame`) — before 19.5 M0 they read `./save/world-default`, and a player's Modified crater chunk injected alien heights AND suppressed the procedural cuts (`Without[Modified]`) into every gate run. **Save/Load (18.9):** full-pool snapshot (`-save-at=N` + `-save-path`, `-load=path`, `-run-ticks=N`; F5/F9 quicksave/quickload in-game); continuity gate `scripts/saveload_gate.sh` — the loaded run's hash log must byte-match the continuous run's suffix. Every NEW component needs a row in `systems/save_spec.go` (VerifySaveSpec fails the save otherwise; memcpy policy requires plain data — no strings/slices/maps); systems with private cross-tick state implement `core.PostLoadHook`. Forensics: `RTS_HASH_EVERY=1`, `RTS_DUMP_AT=N` + `RTS_DUMP_FILE=path`. Debug prints sit behind `RTS_DEBUG=1`. NOTE: `core.SerialThresholdHint = 64` — scenes under 64 units run ParallelFor* inline, so `-race` validation of parallel paths needs the threshold temporarily set to 0 or a 64+ unit scene.

**InitUI pattern.** Despite the name, this has nothing to do with UI — every system has an `InitUI(w *ecs.World)` method that pre-builds its `ecs.Map` and `ecs.Filter` instances. Filters/Maps must be constructed after the world exists; reusing them across ticks avoids per-frame allocation. Always call `sys.InitUI(app.World)` in `registerSystems` (`boot_systems.go`) before `app.AddSystem(sys)`.

**Deferred archetype changes.** Systems that add/remove marker components (`LODSystem`, `StreamingSystem`) collect mutations into a local slice during iteration, then apply them after the query loop — Ark forbids archetype changes while a query is live. Follow the same pattern in any new system that mutates components.

**Singleton resources.** Single-source-of-truth state goes through `ecs.Resource[T]` instead of search queries. Resources must be added via `ecs.AddResource` *before* any system's `InitUI` runs (systems grab a `Resource[T]` handle there and panic if the resource isn't registered). Currently registered:

- `StreamingMap` (smart-space graph state).
- `TerrainChunkIndex` (chunk coord → entity, used by `Stamper` and streaming).
- `PropChunkIndex` (chunk → spawned-prop entities, drained on evict).
- `PropTypeRegistry` (`PropType` → meta).
- `Rivers`, `RoadGraph`, `TrenchNetwork`, `BuildingPlanList` — hand-authored world data; mutated only at startup (`PreprocessRoadGraph`).
- `BuildingChildIndex` (building root → live children, drained on evict).
- `TransitionRegistry` (Phase 7) — NavNode → outgoing TransitionEdge list. Rebuilt by `SpatialBakeSystem` Pass 4 whenever any floor is freshly baked (wipe + repopulate from all live Floor/Door/Stairs entities). `TerrainStreamingSystem.evict` also drops edges whose `Owner` (or whose endpoint Floor entity) just despawned, so eviction during gameplay doesn't leave dangling NavNodes.
- `OrderHistory` (Phase Timeline) — ring of 256 `OrderRecord` tombstones (keyed by `Commander`, which is a squad OR a soloist — see below), `ResCodec` (survives save/load like `EventLog`). An Order entity is the ONLY record of itself and is removed one tick after it goes terminal, so anything that must outlive it is filed here. Written from exactly two places, always immediately before `RemoveEntity`: `SquadService.RecordOrderEnd` called from the resolver's terminal branch (Completed / Failed) and from `cancelChain` (Cancelled, including queued legs that never ran). A looping Patrol's auto-reissue deliberately files nothing — a lap is not an ending, and 120 laps/hour would flush every other squad out of the ring. Consumed by the plan timeline.

**Commandable ≠ squad** (Phase 20.7 L0). `OrderQueueHead` is what makes an entity able to hold an order of its own; the `Squad` MARKER is what makes it behave like a squad. Those were the same thing until a lone vehicle needed a plan the player could see — every surface answering "what is this doing" (map order markers, timeline rows, inspector order block) reads Orders, and `pushSoloMove` wrote an `ActionQueue` with no order behind it. Now `SquadService.ensureCommandable` gives a soloist an `OrderQueueHead` **plus a `CommandRoster` of one** on its first order, and `dropSoloCommand` takes both back when it joins a squad (two commanders for one body is how an order outlives its own cancellation). The self-roster is the whole trick: the six places in the resolver that ask `rosterMap.Get(commander)` answer correctly without one call site learning soloists exist. What a soloist must NEVER acquire is the `Squad` marker — `FormationSystem`, `SquadBrainSystem`, `SquadMacroPathSystem`, `SurvivalInstinctSystem` and `MapMarkerCacheSystem` all filter on it, and a truck has no business growing a formation. `OrderResolverSystem` filters on `CommandRoster + OrderQueueHead`; `OrderOwner.Commander` and `OrderRecord.Commander` are named for what they hold. Execution: a squad's members are driven by FormationSystem off the macro path, a soloist's queue is written by `driveSoloCommander` in the ISSUING tick (a tick of delay would be a behaviour change hidden in a refactor) — and that call must also `clearRoute` + `resetWatchdog`, because the order's completion ring (`rampPopRadius+0.5`) is wider than the driver's own (`rampPopRadius`), so the next leg arrives before the driver ever reaches the arrival branch where it would have reset its stuck/orbit memory itself. Without that, the watchdog measures the new 100 m target against the old leg's best distance, never sees an improvement, declares an orbit and empties the queue. Locked by `ai_solo_orders`.

**A\* admissibility is a two-part product** (`nav_service.go`, Phase 19.8). `nodeHeuristic` charges Chebyshev distance × the cheapest metre a *style* can buy: `navCostRoad` × `styleMinMul(style)`. Both factors matter — `styleCellCost` discounts a road cell ×0.5 under `RoadPrefer` and a cover-rich one ×0.7 under `CoverSeek`, so a heuristic built on the bare cell cost overestimates 2:1 and the search goes greedy exactly where the player picked a style. Change a style multiplier ⇒ change `styleMinMul`; `TestStyleMinMulIsTheActualMinimum` sweeps the `NavCell` value space and will catch the drift. **Diagonals deliberately do not test the corner they cut.** The standard occupancy-grid check closes the only way into a building here: a door's outside cell IS a footprint cell, walkable solely through `cellAt`'s transition exception, and its facade neighbours are blocked on purpose (measured: `ai_main_m1` 0/8 entering, `ai_clear_building` 12.3 → 110.3 s). Bodies are kept out of walls one layer down, by `UnitMovementSystem`'s wall clip, which slides instead of jamming.

**Rendering reads global camera.** `systems.CurrentCamera` is a package-level `rl.Camera3D` updated by `CameraSystem` each tick. The main loop reads it for `rl.BeginMode3D`. `systems.CurrentOriginChunk` (also updated by `CameraSystem`) is the chunk used as the origin when converting `WorldPos → render space` so float32 precision stays bounded near the camera no matter how far the anchor has travelled.

### Per-tick pipeline (terrain + world systems)

Order matters; this is `main.go`'s registration order:

1. `terrain_streaming` — every 250 ms. Spawns chunks within range, evicts out-of-range. On eviction: `WriteChunk` for `Modified` chunks, despawn props via `PropChunkIndex`, despawn building children via `BuildingChildIndex` (root-keyed), `UnloadMesh`, `RemoveEntity`.
2. `terrain_load` — every tick. For each `HeightmapDirty` chunk, `ReadChunk(SaveDir, cc, &heights)`. Hit ⇒ `Heightmap + Modified`, clear dirty. Miss/error ⇒ leave for procgen. Errors logged, never fatal.
3. `terrain_gen` — every tick. Fills `HeightmapDirty` chunks via `GroundHeight(x, z)` (deterministic fBm-Perlin), then clears `HeightmapDirty`.
4. `river` — for each pristine chunk crossing a polyline, cuts the bed.
5. `road` — flatten + road / bridge / junction props for chunks intersecting any `RoadGraph` edge.
6. `building` — terrain pass (bunker `RectCut`) + child pass (walls / floors / stairs / openings) for any `Building` rooted in this chunk.
7. `trench` — earthwork polyline cuts.
8. `prop_spawn` — vegetation + rocks. Reads rivers, roads, buildings, trenches for clearance.
9. `spatial_bake` — NavGrid + CoverMap + cover slots + FloorNavGrid + TransitionRegistry (Phase 6/7).
10. `terrain_mesh` — rebuilds `MeshDirty` chunks (Active full-res 65×65, Relevant decimated 33×33) with skirts; uploads via `rl.UploadMesh`. Old mesh freed via `rl.UnloadMesh` (NOT `UnloadModel`, which would `C.free` Go pointers — see comment on `components.ChunkMesh`).
11. `ground_stick` — floor-aware Y clamp for anchor + units; everything on a carriageway rides `RoadSurface.DeckY`.
12. `unit_movement` (Phase 7) — drains `ActionQueue`; separation steering.
12b. `vehicle_driver` (Phase 19) — kinematic Driver: RoadGraph-маршрут для головного MoveTo (RoadRouter), road/offroad скорости, RoadFollower, реверс.
12c. `air_traffic` / `air_driver` (Phase 20 M0) — расписание прибытий (`AirArrival` → `AircraftFactory.Spawn`) и уход за край; кинематический полёт по `ActionQueue` с липкими дилами скорости и высоты, суб-шаг по скорости (терраин пересэмплируется раз в шаг), огибающая торможения только на последней ноге. Уход за край ОБЯЗАН вычищать Awareness (`sweepAwarenessOf`, общий с DamageService) — иначе наблюдатель у точки ухода держит в FIFO переиспользованный id (M2, SIM PANIC в utility). M2: драйвер исполняет живой `AircraftOverride` (Break/Flare = жёсткий отворот от `ThreatYaw` + полный газ + нырок к `airEvadeAGL`, дил высоты не трогается; Abort сведён к обычному egress через `SendHome`).
12d. `missile` (Phase 20 M2) — полёт каждой живой ракеты ДО `contact`, чтобы попадание тика было в картине тика: наведение поворотом вектора скорости под лимитом `TurnRad`, топливо, взрыватель близости по ЗАМЕТАЕМОМУ отрезку (быстрый пересекающий не перешагнёт радиус за тик), один розыгрыш ловушек в терминальном окне против цели с живым `AirReflexFlare`. Урон через `DamageService` (→ `EventAirDown`).
13. `contact` (Phase 18.5) — sensor detect + `Awareness` writeback + `Contact` upsert (заменил Phase 7 `vision`; Active-tier only) + пассивный проход по излучателям (Phase 20 M1) — ESM-пеленг без дальности, отдельным апсертом после зрительного.
14. `weapon` (Phase 14) — focus fire (19.5 MC3): `pickTarget` returns the enemy named by the squad's head `AttackTarget` order the moment that entry passes the ordinary gates (alive / hostile / in range / class multiplier / own-LOS for shared sightings); everything else in the ranking is the free-choice fallback. Same call serves infantry and `weapon_gunner.go`, so a turret obeys the order too. Parallel raycast combat loop: serial snapshot (eligible seers + target candidates + walls по чанкам) → `ParallelForIndexed` per-shot raycast → serial post-pass (DamageService.Apply, ThreatSource spawn, propagateSuppression, particle bursts — Phase 14.5 particle pool, ECS entities). Реализует RoE gate (`shouldFire`: FireOnInf для пехотных целей, FireOnArm для техники) + AttackMove flag. Phase 19 M3: техника — и цель (класс + секторная броня в targetSnap), и стрелок (`weapon_gunner.go`: пер-ствольный pickTarget, слюящаяся башня, огонь в допуске, стабилизация-штраф на ходу); сплэш опрашивает оба spatial-хеша.
15. `threat_decay` (Phase 14) — despawn'ит `ThreatSource` entities после их TTL И `SmokeField` по `ExpiresAt` (M4). Тонкий serial pass; Phase 15 SurvivalInstinct будет читать живые ThreatSource'ы для cover-slot selection.
15b. `vehicle_reflex` (Phase 19 M4) — arms `VehicleOverride` (FaceThreat/SmokeAndReverse/Flee; M2 добавил GoDark — зенитный расчёт глушит радар под огнём, на который не может ответить, и включает обратно по таймеру; «return fire beats flinch» уже давал нужный гейт: пока пушка отвечает — радар работает) when a vehicle's Threat spikes and it isn't already engaging a visible foe; the driver reads it next tick.

17. `squad_macro_path` / `formation` / `lod`, `movement`, `spatial_audio`, `streaming`, `orbit`, `camera` — unchanged.

**Why river / road / building / trench all run before `terrain_mesh`:** all four mutate the heightmap of pristine chunks; the mesh pass picks up `MeshDirty` once after every cut/flatten in this tick.

Marker semantics, consistent across all systems:

- `HeightmapDirty` = "no heights yet, needs initial fill". Set only at chunk creation. *Not* used to signal in-place edits.
- `MeshDirty` = "GPU mesh must be rebuilt". Set on heightmap edits and on LOD-tier transitions (different vertex resolution).
- `Modified` = "heights diverge from procgen". Set ONLY by `Stamper.StampHeightmap` (player edits) and `TerrainLoadSystem` (chunk loaded from disk). The procedural cuts (`RiverCut`, `RoadCarve`, `RectCut`, `Trench`) deliberately do NOT set `Modified` — they're derivable from the `Rivers` / `RoadGraph` / `BuildingPlanList` / `TrenchNetwork` resources, so re-applying on chunk respawn is free and pristine chunks have zero disk footprint.
- `*Processed` markers (`RiverProcessed`, `RoadProcessed`, `BuildingsProcessed`, `BuildingTerrainProcessed`, `TrenchProcessed`) gate one-shot per-chunk passes. Heightmap-mutating markers also gate `Without[Modified]` so player edits aren't doubled up; entity-spawning markers (e.g. `BuildingsProcessed`) do NOT, so building visuals stay alive on player-edited chunks.

### Persisted world data

`./save/world-default/chunks/{x}_{z}.bin` — one file per `Modified` chunk, binary v1: 4-byte magic `RTSC`, version uint16, flags uint16, ChunkCoord (int32 X, int32 Z), then `ChunkResolution²` × float32 heights LE. Total 16 916 B at current resolution. Atomic via `.tmp + os.Rename`. `/save/` is gitignored.

The persistence API (`WriteChunk` / `ReadChunk`) is intentionally minimal so the on-disk shape can later migrate to region-files without changing callers. `FlushModifiedChunks(world, saveDir)` is `defer`-installed in `main.go` right after `core.NewApp()` so LIFO runs it before window/audio teardown.

Only `Modified` chunks are persisted. Procedural cuts (rivers, road flatten, bunker `RectCut`, trenches) are derivable from world resources and are re-applied at chunk respawn — pristine chunks have zero disk footprint, and the format format v1 has not changed since Phase 2.

### Building lifecycle

A building has two layers:

- **Root** — `Building + WorldPos + AlwaysActive`, created at startup from `BuildingPlanList`. Survives chunk eviction so cross-chunk queries (clearance, AI targeting) keep seeing the building.
- **Children** — walls / floors / stairs / openings, all `BuildingMember + WorldPos + LODRelevant + (WallSegment | Floor | Stairs)` (plus `Door` / `Window` / `Occupancy` / `CoverDirection` / `ShootingArc` on opening segments). Spawned by `BuildingSystem` whenever the host chunk is in stream range; torn down by `TerrainStreamingSystem.evict` via `BuildingChildIndex` (root-keyed).

Per-building constraint (Phase 5): footprint must lie inside one chunk so children share a single `Pos.Chunk`. Multi-chunk buildings are deferred to Phase 15.

Phase 5 writes Smart-Object data (`CoverDirection` on every wall, `ShootingArc` on every window, `Occupancy` on doors and windows) but no system reads it yet. Consumers arrive in Phase 6 (CoverMap) and Phase 10 (TacticalAI).

### Startup entity creation (`boot_scene.go`)

Uses `ecs.NewMap[T]` to add components to new entities, with factory bundles in `entities/` for kinds that need a long component list (units, vehicles). Called from `main()` in this order — **the order is load-bearing**: Ark assigns component IDs on first registration, and moving a `NewMap` / spawn across another one can shift archetype layout and therefore iteration order, which the replay hash will catch.

1. `spawnAnchorAndCamera()` — anchor (`WorldPos + LODActive + LODAnchor + AlwaysActive + OnGround`) and the orbit camera (`WorldPos + Camera + OrbitController + ActiveCamera`). Skipped under `-load`.
2. `spawnWorldRoots()` — one root per `BuildingPlan` (`WorldPos + Building + AlwaysActive`, children spawn lazily per chunk) plus its `Level` entities, and one `TrenchRoot` per polyline so hit-tests can return an entity.
3. `initGameplayHandles()` — the unit / order / squad Map handles the UI and input halves read, plus `UnitFactory` / `VehicleFactory` / `RoleService`.
4. `spawnScene()` — a scripted `-scene` harness, or the default playground squads + FoW dummies + one vehicle per class. No-op under `-load`.
5. `loadSnapshot()` — restores a full-world snapshot and re-binds anchor + camera (the snapshot does not preserve those handles by name).
6. `initRenderHandles()` — query handles and the render context structs (`HitTester`, `ghostContext`, `routePreviewCtx`, `orderMarkerCtx`, `ParticleRenderCtx`).

Units go through `entities.NewUnitFactory(world, posMap)` + `Spawn(pos)` — bundles 11 unit-only Map handles so callers don't re-wire `ecs.NewMap[Stance]` / `[Motion]` / `[Threat]` / ... per call site. The `Stamper` service is built in `initServices()` and used from input handling (`KeyX`).

### Profiler & file trace (Phase 7.5)

`core.Profiler` records the last `ProfileWindow=60` frames. Tick-total and per-system durations come from `time.Since` brackets in `App.Tick`. Reads (`MedianTick`, `MedianSystem`, `PrintSnapshot`) are non-allocating on the hot path; HUD draw cost is dominated by `MeasureTextEx`/`DrawTextEx`, not the median sort.

**Stdout snapshot.** Press `Ctrl+P` in-game. Two-column table (system → median ms over current window) prints to stdout — copy/paste into issues / commit messages / this file for before-after comparisons. Tracer (if open) also gets a `{"event":"mark","label":"snapshot"}` line so you can correlate the dump with the captured JSONL.

**Hitch logger (always on, interactive).** A frame that is both >30 ms and >2.5× the rolling frame median prints one rate-limited line: `[hitch] frame X ms (median Y) tick Z ms | top-3 systems of that tick`. `tick ≪ frame` means the spike is render-side (draw calls / uploads), not sim — attribution without a trace build (`dev_tools.go:hitchCheck`, ISSUES #15).

**File trace.** Built behind the `trace` build tag. The non-trace build is the default and pays zero overhead — `Tracer`'s methods compile to empty bodies (see `core/trace_off.go`).

```bash
# Build & run with tracing enabled.
go build -tags trace -o rts .
./rts -trace=/tmp/run.jsonl

# Per-frame JSONL: one record per frame plus marker records.
# Frame record: {"frame":N,"elapsed_ms":...,"fps":...,"frame_ms":...,
#                "tick_ms":...,"systems":{name→ms},
#                "entities":{archetype→count},"heap_mb":...}
# Mark record:  {"event":"mark","label":...,"frame":N,"elapsed_ms":...}

# Press M in-game to drop a manual mark into the active trace.

# Common queries.
jq -r '.tick_ms' /tmp/run.jsonl | head            # tick ms histogram source
jq 'select(.event=="mark")'  /tmp/run.jsonl       # marker lines only
jq '.systems.terrain_mesh'   /tmp/run.jsonl       # one system over time
```

**Watching a scripted scene.** `-scene=ai_* -watch` renders the scene instead of
running it headless: the synthetic stimuli (barrage pulses, deep-magazine
gunners, staged defenders) live in the harness, so this is the only way to
*watch* a shelled squad or a bounding march. Verdict lines still print. Gates
never pass the flag, so a gate run is byte-identical with or without it.

**Frame capture.** `-shot=name.png -shot-at=<frame>` renders normally, writes a
PNG (relative to the working directory — raylib prepends it) and exits;
`-shot-cam=radius,pitchDeg,yawDeg` overrides the starting orbit, and
`-shot-select=N` / `-shot-select-veh=N` / `-shot-select-air=N` / `-shot-order=x,z[;x,z]` / `-shot-scroll=px` populate, order and scroll
the inspector so panel work can be captured at all, and `-shot-panel=<kind>` swaps the
Inspector leaf for any widget (`behavior`, `symbology`, …) that the default
layout doesn't show. A `-shot` run never saves the layout — the swap is
throwaway and must not leak into the player's saved one. **The capture forces a
render-batch flush first** (scissor pair before `TakeScreenshot`): raylib
batches draw calls, so without it everything issued since the last flush is
missing from the PNG — and because the stale back-buffer pixels underneath are
identical for static chrome, the shot still *looks* complete. Any widget drawn
late in `drawUI` was simply invisible to captures before 2026-08-02. Enough to eyeball a render change without a live
session; it does not replace a playtest for anything interactive.

The trace file is written through `bufio.Writer` (4 KiB) — kill -9 may truncate the tail; clean shutdown via `WindowShouldClose` flushes via the deferred `app.Trace.Close()` in `main.go`. Format is JSONL v1; field names match the PHASE-7.5 plan and are stable, so `jq` filters from one capture keep working across optimization runs.

### Adding a new system

1. Define a struct in `systems/` with embedded `*ecs.Map[T]` / `*ecs.Filter…[T,…]` fields it needs.
2. Implement `Name() string`, `LODPolicy() core.LODPolicy`, `Update(ctx core.UpdateContext)`, and `InitUI(w *ecs.World)` (which constructs the Filters/Maps).
3. In `registerSystems` (`boot_systems.go`) — the single seam for this — instantiate the struct, call `sys.InitUI(app.World)`, then `app.AddSystem(sys)`. Order matters: `InitUI` must run after the world is created and before the first `Tick`, and the `AddSystem` sequence *is* the per-tick pipeline order. Resources used via `ecs.NewResource[T]` in `InitUI` must be `ecs.AddResource`'d *before* `InitUI` runs (i.e. in `initResources`, `boot.go`). Nothing from this function escapes to the caller — the frame loop never sees a system handle.
4. If `Update` mutates archetypes (adds/removes components), batch the changes and apply them after closing the query.
5. For "called on demand" behaviour (terrain stamps, future ballistics impacts), prefer a service object with the same pre-built-handles pattern over a System — see `Stamper` in `systems/stamp.go`.
6. **Parallel-aware systems.** When using `sys.pool.ParallelFor` / `ParallelForIndexed`, follow the Phase 11.6 pattern: keep snapshot buffers as struct fields and reset them with `buf = buf[:0]` (or `clear(map)`) at the top of `Update`, not `make(...)`. Workers must write only to their own snapshot range / per-worker scratch buffer; never to a shared slice/map. Run `go test -race ./core/` after touching `core/worker_pool.go`, and `go run -race . -workers=4` for 30 s of in-game motion when touching one of the parallel systems (UnitMovement / Vision / Formation / SquadMacroPath). The race detector catches almost every concurrent write — false-sharing on cache lines is the remaining hole, deferred to Phase 14+ profiling.

### Multi-file system layout

Large systems (~600+ lines) live in a small `XXX.go` orchestrator file plus sibling files in the same package. Pattern: the orchestrator keeps the struct, `InitUI`, `Name`/`LODPolicy`, and a slim `Update` that delegates to extracted methods. The siblings hold pass / phase bodies as `func (sys *XSystem) ...` — Go binds methods across files in the same package, so call sites don't change.

### Additional Codestyle

1. Try to write clean, concise code.
2. Comments: as few as possible — they scatter and go stale while code moves on. Prefer self-explanatory code; a genuinely non-obvious invariant gets one short line, never a paragraph.
