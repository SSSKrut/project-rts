Целевая картина — у каждой поверхности одна работа:

| Поверхность | Вопрос игрока | Режим |
|---|---|---|
| **Squad bar** (карточки, низ 3D) | «кто у меня в руках, у кого какое оружие» | команда, 1 клик |

| **Behavior widget** | «как они себя ведут по умолчанию» | настройка, по требованию |
| Timeline | «что запланировано» | чтение |
| Map | «обстановка» | команда/чтение |

## Что в Phase 17.7 сознательно НЕТ

- **Полный MoW-инвентарь** (drag-and-drop, подбор оружия с земли) — Equipment
  фиксирован per-role; пересмотр не раньше engineering-фазы.
- **Вкладки в инспекторе** — вкладки прячут статус; годятся для конфигурации
  (Behavior widget = отдельная панель), не для glance-поверхности.
- **Collapse/агрегация карточек** при мультисквадном overflow («3×AK 1×PKM» с
  разворотом) — в MVP простой clip по ширине; механика схлопывания по жалобе.
- **Bar над картой / в Command-preset** — bar живёт только на Panel3D; если
  плейтест покажет, что в Command-preset (3D маленький) им пользоваться
  невозможно — отдельным решением.
- **Focus ≠ Selection** (карточка «фокусирует», приказы всё ещё отряду) —
  отклонено, см. P4.
- **Иконки-текстуры оружия** — текстовые глифы (short-name из WeaponSpec) до
  icon-pipeline Phase 17.5. Все строки ASCII (raylib-шрифт без кириллицы).
- **Drag-and-drop бойцов между отрядами** (GAMEDESIGN упоминает) — UI expansion.
- **Formation editor / Symbology / Timeline** — не трогаем вообще.

## P-решения

**P1. Разделение по частоте, не по типу сущности.** Диспетчер selection-kind
(unit/vehicle/squad/contact/multi) остаётся как есть; расчленяется содержимое:
командные действия → bar, конфигурация → Behavior widget, статус → инспектор.

**P2. Squad bar — оверлейная полоса по нижнему краю Panel3D, не workspace-виджет.**
Bar — эфемерный selection-bound UI (как marquee и building popup), а не панель,
за которую воюют сплиттеры. Автоскрытие при пустом выделении. Высота ~72 px,
рисуется после `Scene3DRT.Composite` в скиссоре Panel3DContent (рядом с
role-labels блоком в `frame_draw.go`).

**P3. Bar привязан к отрядам, затронутым выделением (+ солисты), не к самому
выделению.** Клик по карточке сужает выделение до бойца — bar НЕ схлопывается,
продолжает показывать весь отряд с подсветкой выбранного. Иначе первый
drill-down уничтожает поверхность, с которой работаешь. Привязка пересчитывается
из `Sel.Units → SquadMember.Squad` каждый кадр (плюс bar-side удержание, см. P5).

**P4. Клик по карточке = замена выделения одним бойцом.** Shift+клик = toggle
(консистентно с 3D-LMB). Клик по цветовому чипу отряда в начале его группы =
выделить весь отряд. Альтернатива «focus ≠ selection» (инспектор показывает
бойца, приказы идут отряду) отклонена: вводит второе понятие во всю систему
выделения (Sel.Units, hover, маркеры, карта) ради редкого кейса. Клики идут
request-паттерном (`ui.SelectUnitRequest` рядом с `SelectSquadRequest`),
консюмятся в `frame_draw.go`.

**P5. Позиционная стабильность карточек.** Порядок = roster slot order, никаких
сортировок по дистанции/ID. KIA-карточка остаётся на месте серой с меткой —
**ростер тут не поможет**: смерть вызывает `squadService.Leave(unit)` прямо из
`DamageService` (`systems/damage.go:100`), член исчезает из ростера в тот же
тик. Поэтому tombstone — состояние виджета (bar держит последний снапшот состава
per-squad; исчезнувший член рисуется тумбстоуном TTL ~5 с или до смены
привязки). Это UI-side память, в ECS/save не попадает.

**P6. Per-weapon intent (aim mode) — отдельный stretch-милстоун M5.** MVP bar'а
самодостаточен: карточки + выбор юнита. Клик по оружейному слоту → aim mode →
клик по цели создаёт Order с weapon-pref — это слой 3 таксономии COMMAND-MODEL
§4, тянет новый order-param компонент + логику в WeaponSystem. Может уехать в
Phase 21 (RoE/weapons polish), закрытие фазы не блокирует.

**P7. Behavior widget — stateless immediate-mode, НЕ singleton с состоянием.**
В отличие от Formation editor (zoom/drag/presets), у standing rules всё
состояние в ECS-компонентах — виджет = чистая функция `DrawBehaviorPanel(panel,
BehaviorCtx)`. Новый `PanelID = PanelBehavior` добавляется в
`WorkspacePanelKinds` (`ui/layout.go:92`) — chevron menu, corner-split
(`corner.go:453`) и floating switch-menu подхватывают его автоматически, отдельной
проводки не нужно. В `scrollablePanels` (`frame_ui.go:133`) — секции высокие.

**P8. Единый визуальный словарь.** Карточка = композиция существующих примитивов
`widget.go` (Chip / Bar / TextCentered / RoleColor-чип); RoE-блокировки — те же
пилюли со strike-through, что в order-row. Нового стиля не появляется; палитра
bar'а = InspectorStyle.

**P9. Инспектор после slim = header + status + orders + override/reason +
roster-как-навигация.** Ветки unit / vehicle / multi / contact переезжают с
легаси `drawText + y += inspectorRowH` на Column/widget-примитивы (заодно
получают знание ширины — сейчас длинные строки уезжают под скроллбар); кнопки
contact-панели становятся Chip'ами. Roster-строки получают клик
(`SelectUnitRequest`) — дубль bar'а для случая, когда юнит не виден в 3D.

**P10. Input shielding через frame contract.** Порядок фаз кадра: input → sim →
draw. Bar-rect обязан быть известен ДО `handleInput`, иначе клик по карточке
провалится в 3D (marquee/приказ). `beginFrame` считает `g.Frame.SquadBarRect`
детерминированной функцией (Panel3D bounds + есть-ли-выделение); handleInput
гейтит 3D-клики по нему — так же, как floaters шилдят input.

**P11. Хоткей Behavior-виджета — `Q`** (решено в M1). ROADMAP предлагал `R` —
занят (`debugOverlay.Roofs`); `B` занят (InteriorOpen); `U` тоже оказался занят
(выход из отряда, `frame_orders.go:220`). Свободны были только `C/J/L/Q/Y`, из
них `C` зарезервирован под cover-оверлей, `Z/X/C` — под stance в Phase 21.
`Q` выбран как сосед `E` (редактор формации) под левой рукой. Паттерн тот же:
toggle floating.

### M5 — Per-weapon intent — ОТЛОЖЕН В PHASE 21 (2026-08-02)

**Почему.** COMMAND-MODEL §5 требует, чтобы weapon-pref висел на `AttackTarget`
Order'е **owner-юнита** (канонический пример: два танка получают каждый свой
приказ со своим стволом). Под этим не оказалось фундамента:

1. **Приказы адресуются только отряду.** `OrderQueueHead` живёт на squad;
   `dispatchOrder` (`command.go:395`) отправляет солистам `pushSoloMove` —
   то есть одиночная машина «приказ атаковать» не держит вовсе, а «атака»
   для неё вырождается в поход к точке.
2. **`AttackTarget` не наводит огонь** (ISSUES #28). Weapon-код не читает
   `OrderTarget` ни в одной строчке: приказ только снимает HoldFire через
   `OverridesHoldFire`, цель каждый ствол выбирает сам.

Отсюда: сделать M5 «отрядным параметром» — значит получить семантику, прямо
противоречащую канону (клик по пушке танка А отдаёт приказ всему отряду).
Честный M5 = сначала per-unit order layer + focus fire, это отдельная работа
уровня фазы, а не хвост UI-фазы. Прерогативы записаны в ISSUES #28 и в
ROADMAP Phase 21.

**Что уже готово под него в 17.7:** карточка знает свои стволы и рисует их
пер-ствольно; клик по карточке уже ходит через request-паттерн, так что
aim-mode подключается одним новым состоянием, когда сим будет готов.

### M5 (исходная формулировка, для справки)

- Клик по оружейному слоту карточки → aim mode (курсор меняется, ESC/RMB —
  отмена); следующий клик по цели → `AttackTarget` + новый POD
  `OrderParamWeaponPref{Kind WeaponKind}` → **строка в `save_spec.go`**
  (VerifySaveSpec поймает).
- `weapon_fire_gate.go` / `weapon_gunner.go`: pickTarget уважает pref у
  юнита/ствола-носителя. RoE-гейт не меняется; HoldFire → strike-through слот
  (словарь AT-пилюли).
- Гейты обязательны: replay + saveload полный прогон (новый компонент в хеш не
  входит, но save_spec — да).
